# Yandex Disk Rescue 1.0.4 — руководство

[На главную](README.md) · [English](GUIDE.en.md) · [Релизы](https://github.com/fefenke/Yandex-Disk-Rescue/releases)

## 1. Что скачивает программа

Поддерживается обычный раздел «Файлы» Яндекс Диска. Безлимитная автозагрузка фото и видео не учитывается и не скачивается. Программа использует технологию API Яндекс Диска или официальный клиент, повторяет обращения к доступным файлам и сохраняет результаты. Она не чинит облачные оригиналы, не восстанавливает удалённые файлы и не гарантирует обход серверной недоступности.

Нужны Windows 10 1709+ или Windows 11 и .NET Framework 4.7.1+. Выберите x64 для 64-битной Windows либо x86 для 32-битной; x86 также работает на x64. ARM64 отдельно не выпускается.

## 2. Установка и первый запуск

1. Скачайте ZIP нужной архитектуры из релиза и распакуйте его целиком в постоянную папку с правом записи.
2. Запустите Start Yandex Disk Rescue.cmd: он проверяет окружение и запускает программу. Приложение открывает «Настройки».
3. Выберите API или официальный клиент. Заполните обязательные поля, выберите режим прохода и нажмите «Начать проход» сверху.
4. Гайд открывается верхней кнопкой. Во время прохода и автоматических повторов параметры загрузки заблокированы. Для изменения нажмите «Остановить» и дождитесь завершения.

Рядом с программой создаётся data с настройками, историей, списками, отчётами и зашифрованным токеном. У разных распакованных копий своя история. Не запускайте новую копию с ожиданием, что она автоматически использует данные другой.

## 3. Способ через API

Официальный клиент не нужен. Откройте OAuth-ссылку в настройках, войдите в нужный аккаунт Яндекса, получите токен и вставьте его в поле. Токен даёт доступ к аккаунту: не отправляйте его другим людям и не включайте в сообщения об ошибках.

Выберите обычную локальную папку сохранения, например папку бэкапа на HDD. Не используйте облачные заглушки, ссылки и точки перенаправления. Структура облачных папок сохраняется. Облачный путь disk:/ означает весь обычный раздел; disk:/Фото — одну папку. Переключение аккаунта или пути создаёт отдельный контекст истории.

Обычно подходит режим «Повторить все нескачанные» и сохранённый список. В первый раз список получается автоматически.

## 4. Способ через официальный клиент

Установите клиент Яндекс Диска, войдите в аккаунт и дождитесь синхронизации списка файлов. В приложении выберите его локальную папку Диска. OAuth-токен в это приложение вводить не нужно.

Программа запрашивает получение файлов и следит за результатом; сетевой загрузкой управляют Windows и официальный клиент. Если включён перезапуск клиента при ошибках, приложение может перезапускать его. Параметры запросов ссылок и HTTP-докачка частей относятся к API, а не к клиентскому способу. Контрольные точки 32 МиБ / 15 секунд тоже относятся только к API.

## 5. Список из облака и режим прохода

Это разные настройки. Сохранённый список избавляет от повторного обхода перед каждой попыткой. При его отсутствии начинается сканирование; прерванный обход продолжается с сохранённой позиции. Для новых, изменённых или удалённых облачных файлов выберите обновление списка. Само обновление не заставляет повторно скачивать подходящие готовые файлы.

Перед докачкой начатого файла дополнительно запрашиваются его свежие размер, дата изменения и доступный MD5. Это один запрос для конкретного файла, а не новый обход Диска. При недоступности этих сведений части сохраняются, попытка откладывается. Обнаруженная смена версии запрещает смешивать старые и новые данные. Исправленные сведения списка записываются после завершения активных задач: в конце прохода, при ручной остановке или обработанной ошибке.

Ошибки сканирования видны в журнале и предупреждении. Завершение обхода ещё не доказывает, что все облачные папки были доступны. Количество скачанных относится к найденным файлам; полнота Диска при ошибках не гарантируется. После резкого вылета может остаться прежний целый список; свежая версия начатого файла проверяется при следующей докачке.

Режимы прохода:

- «Продолжить незавершённый» — ещё не обработанные файлы и отменённые попытки; не все ранее завершившиеся ошибки.
- «Повторить ошибки сервера / синхронизации» — записанные ошибки соответствующего типа.
- «Повторить таймауты и сбои» — прерванные, зависшие и другие неудачные загрузки.
- «Повторить все нескачанные» — всё без подходящей готовой локальной копии; обычный выбор для повторов.
- «Начать проход с начала» — проверить весь список с начала. Подходящие готовые файлы повторно не скачиваются.
- «Докачать начатые файлы · API» — только файлы с данными в .ydr-part или .ydr-segments. Автоповтор сохраняет эту очередь.

## 6. Два таймаута и общая очередь

«Ожидание ссылки» — ответ API после отправки запроса; по умолчанию 3 секунды, диапазон 1–60. Очередь, выбранный интервал API и общий cooldown не расходуют этот бюджет.

«Без данных файла» — ожидание ответа скачивания и новых байтов; по умолчанию 3 секунды, диапазон 1–60. Таймаут отдельный для каждого потока и сбрасывается на заголовках ответа и новых данных. Это не ограничение общей длительности скачивания: файл может качаться часами, пока данные поступают. Проверка сохранённых частей выполняется до запроса и вне сетевого таймаута. Через официальный клиент это поле ограничивает отсутствие прогресса получения файла.

До двух дополнительных попыток допускаются, если в текущей попытке записаны новые байты, а затем произошёл сетевой обрыв, таймаут или неполный ответ. Повтор использует ту же ссылку, продолжает данные и заново встаёт в хвост общей очереди соединений. Его таймаут равен выбранному +2 секунды для обоих повторов: 3 → 5 → 5. Даже небольшой новый прогресс может дать следующий повтор в пределах этого лимита.

Если новых байтов нет, быстрые повторы заканчиваются: файл остаётся для следующего подходящего прохода. Старые сохранённые части не считаются новым прогрессом. HTTP-ошибка, неверный Range, несовпадение MD5, ошибка записи и Стоп быстрых повторов не вызывают.

Рабочая ссылка сохраняется только в памяти одной серии автоматических проходов после подтверждения данными. Произвольный срок жизни не предполагается. При отказе или отсутствии новых байтов свежая ссылка запрашивается на следующем проходе, без дополнительной цепочки обновлений прямо в неудачной попытке. Перезапуск приложения или новая ручная серия создают новый кеш ссылок.

## 7. Бесконечные проходы и ограничения API

Бесконечные проходы включены по умолчанию. После обычного прохода начинается подготовка следующего по проблемным файлам без обязательной паузы 30 секунд. Это не обещание мгновенного старта: сохранение отчётов, чтение истории и проверка файлов требуют времени. В режиме докачки сохраняется очередь начатых файлов.

Временная ошибка всего прохода вызывает замедление 1, 2, 4, 8, 16, максимум 30 секунд. Успешное завершение сбрасывает его. Пустая подходящая очередь или неповторимая ошибка заканчивает серию. Стоп отменяет текущий проход и ожидание следующего.

Все REST-запросы API проходят через общий ограничитель. HTTP 429 означает слишком много запросов, 408 — таймаут запроса, 5xx — серверную ошибку. При этих ответах учитывается Retry-After: число секунд или дата, когда допустимо повторить запрос. Без пригодного заголовка ожидание растёт 1, 2, 4, 8, 16, 32, максимум 60 секунд. Указание сервера может требовать большего ожидания.

Интервал API временно увеличивается до 5000 мс и постепенно возвращается к выбранному после устойчивой успешной работы. Настройки пользователя не переписываются; состояние общее для автоматических проходов серии. Интерфейс показывает причину, оставшееся время и временный интервал. Отправленные запросы и скачивания по готовым ссылкам продолжаются. Ошибки storage-сервера не замедляют REST API этим ограничителем. Подготовка, ожидание API и скачивание — разные этапы.

## 8. Параллельность и интервал

По умолчанию до 7 задач получения ссылок и до 20 соединений скачивания. Оба значения настраиваются от 1 до 30 и работают независимо: пока файлы скачиваются, готовятся ссылки следующих. Все части всех файлов входят в один лимит 20; это не 20 файлов по четыре соединения каждому. Очереди ограничены, задача не создаётся сразу на каждый облачный файл.

Интервал API 25–1000 мс, по умолчанию 50 мс: примерно до 40, 20, 10, 5 или 1 запуска в секунду при 25, 50, 100, 200 или 1000 мс. Это частота запусков, а не число ожидающих ответ задач. Пункт 2.2 условий API указывает 40 запросов в секунду: https://yandex.ru/legal/disk_api/ru/ . Ограничитель может временно увеличить интервал при ошибках.

Больше соединений не создаёт дополнительную пропускную способность. Если интернет уже занят целиком, увеличение обычно не ускоряет результат. На HDD параллельная запись разных частей может замедлять диск. При перегрузке попробуйте меньше соединений и 1–2 потока на файл. При простое из-за ожидания серверов параллельность может помочь. Меняйте один параметр и сравнивайте несколько проходов с одинаковыми таймаутами, учитывая успешные файлы и объём, а не только быстроту прохода.

## 9. Части крупных файлов

Настраиваются 1–8 потоков; по умолчанию 4 для файлов от 256 МБ. Порог 64–4096 МБ; МБ = 1 000 000 байт. Новое разделение применяется при известном облачном MD5. Маленькие файлы качаются одним потоком. Значение 1 запрещает разделять новые файлы, но сохранённые части сохраняют план и продолжаются с выбранной параллельностью.

Первый Range-запрос проверяет поддержку сервера; после пригодных заголовков запускаются остальные части. При игнорировании или отказе Range используется обычное скачивание. Неверные диапазоны и MD5 не считаются успехом. Проблемная часть не обязана останавливать другие.

Рядом с назначением хранятся .ydr-part и папка .ydr-segments с планом и отдельными частями. После получения всех частей они собираются, проверяются размер и доступный MD5, затем временный файл становится готовым. Оборванная сборка откатывается и использует готовые части заново. Дополнительно к частям нужно место для собираемой копии, вплоть до размера файла. Прямая запись всех диапазонов в один файл в этой версии не реализована.

## 10. Контрольные точки, HDD и аварийное восстановление

Каждый активный поток сохраняет контрольную точку после 32 МиБ новых данных ИЛИ 15 секунд при поступлении очередных данных — что наступит раньше. После сохранения счётчик байтов и времени начинается заново. Это не пауза на 15 секунд и не таймаут. Например, за 15 секунд накопилось 5 МиБ: сохраняются они; ещё 27 МиБ после этого не вызывают сохранение по порогу 32 МиБ.

При нормальной остановке, обрыве и завершении попытки остаток тоже фиксируется. Сначала данные принудительно сохраняются на диск, затем подтверждается журнал с SHA-256 участков в .ydr-state. При новом запуске проверяются подтверждённые участки; повреждённый или неподтверждённый хвост отбрасывается и скачивается заново. До 32 МиБ неподтверждённого хвоста возможно на каждый активный поток, а не на весь файл или все загрузки вместе.

Не удаляйте .ydr-state, .ydr-part или .ydr-segments до завершения файла. Старые части без журнала могут быть использованы при известном облачном MD5 с последующей финальной проверкой. Смена облачной версии сбрасывает несовместимые данные.

Сохранение выполняется рабочим потоком и кратко задерживает его; другие загрузки могут продолжаться, но делят один диск. На одном SATA HDD/NTFS запись 2 ГиБ без контрольных точек заняла 77,9 с, с SHA-256 и контрольными точками — 84,9 с (+7,0 с, около 9%). Это один синтетический замер, не гарантия скорости другого файла или диска. Восстановление требует чтения сохранённых данных; после реального выключения системный кеш будет холодным, поэтому время нельзя оценивать по повторному чтению из памяти.

Проверены принудительный Kill отдельного процесса во время загрузки и сборки, повреждённые участки, оборванные записи и правильный финальный MD5. Физическое отключение электричества не проводилось. Накопитель и контроллер должны выполнять команды принудительной записи; неисправность или игнорирование flush не позволяют обещать абсолютную сохранность.

## 11. Что означает проверка готового файла

При известном облачном MD5 проверяются размер и контрольная сумма. Для ранее проверенного файла история, версия, размер и время записи позволяют избежать повторного полного чтения. «Начать с начала» выполняет полную сверку; это может занять время на больших файлах. Интерфейс показывает файл, количество проверенных файлов, объём и процент хеширования. До окончания сверки счётчик готовых предварительный.

Без облачного MD5 сейчас достаточно совпадения размера: это слабее и не доказывает совпадение содержимого. Локальный SHA-256 подтверждает сохранённые байты, но не заменяет отсутствующий хеш облачного оригинала. Отдельного строгого статуса для такого случая в 1.0.4 пока нет.

Существующий неподходящий файл сохраняется во время скачивания новой временной копии, но после успешной проверки может заменяться. Режима «никогда не заменять существующие» и отдельного архива старых копий пока нет. Не используйте папку с единственными вручную изменёнными оригиналами как назначение без собственной резервной копии.

## 12. Интерфейс, история и ошибки

«Обзор» показывает категории из списка. «Файлы и папки» — прогресс папок с подпапками и содержимое выбранной папки. Поиск и фильтр оставшихся применяются к выбранной папке. Двойной щелчок открывает готовый файл или папку, контекстное меню предлагает открыть и показать в Проводнике. Незавершённая часть не открывается как готовая.

История и список читаются локально; первый большой журнал загружается в фоне. «Скачано всего» учитывает готовые файлы, «за проход» — новые успехи. Режим влияет на выбранную очередь, а «осталось» относится ко всему списку. Журнал содержит поиск и фильтры; история проходов и отчёты находятся в data.

Таймаут ссылки означает, что скачивание ещё не началось. Таймаут данных означает отсутствие ответа или новых байтов, а не автоматически HTTP 500. HTTP 401 требует проверить токен, 403 — доступ; 429 обрабатывается общим ожиданием API, 500/503 означают серверные ошибки. IOException может относиться к сети или диску: ориентируйтесь на этап, код и журнал. Повторы не гарантируют доступность оригинала.

## 13. Обновление и безопасность

Автопроверка обновлений выполняется при запуске и раз в 6 часов; её можно выключить, ручная проверка остаётся. Установка предлагается в простое и требует подтверждения. ZIP нужной архитектуры проверяется по SHA-256 из GitHub. Приложение закрывается, заменяет программные файлы, сохраняет data и перезапускается; неудачная замена откатывается.

Для ручного обновления сначала закройте программу. Сохраните data и служебные части загрузок, затем замените файлы приложения из целого ZIP. Не перезаписывайте историю работающего экземпляра и не копируйте чужую data. Сохранённый токен зашифрован Windows DPAPI для текущего пользователя Windows, а для запросов используется в памяти.

Не публикуйте data, api-token.bin, журналы с личными путями и подписанные ссылки. При сообщении об ошибке уберите токены, параметры подписанных URL и личные имена файлов. При утечке отзовите доступ в Яндекс ID. Исходники и ZIP релиза не должны содержать пользовательские данные.
