# Стабилизация Windows и переход к единственному API-движку

## Основание и согласованные решения

Базовый коммит: `234fea2f415007a698d0faa834e1136f3d3891fd`, версия 1.1.2.
Пользователь выбрал первый вариант: исправить надёжность, затем убрать клиентский движок и устаревшие режимы. Миграция .NET 10 отложена. Основание: обсуждение аудита и документа `Yandex_Disk_Rescue_Windows_Roadmap_Approval.md` от 18 октября 2026.

- Сохраняются C#, WinForms, .NET Framework 4.7.1, x64/x86 и заявленная Windows 10 1709+ / Windows 11. Фактическая проверка всех старых ОС требует отдельных виртуальных машин.
- Сканирование не расширяет выбранный режим. DownloadErrors не включает новые или изменившиеся версии файлов только из-за обновления списка.
- All на автоматическом повторе переходит в Remaining. Remaining, DownloadErrors и PartialFiles сохраняют свою семантику.
- IntegrityFailures выполняется один проход на ручной запуск. Ограниченные повторы сетевых операций сохраняются; автоматический повтор после несовпадения хеша не вводится.
- Пользовательские данные сохраняются. Старые записи проходов отображаются нейтральным именем; старые журналы клиентского способа остаются на диске и не смешиваются с API-историей.
- Публикация релиза не разрешена этим этапом. Приложение, запущенное пользователем, не заменяется.

## Исправления надёжности

1. Обновления: отдельный таймаут отсутствия данных, отмена пользователем, восстановление UI после отмены/ошибки, исключение prerelease. Сохраняются проверка SHA-256, allowlist и предел 100 MiB. Формат пакета и helper пока не меняются.
2. Настройки и токен: атомарная запись; предыдущая корректная версия настроек сохраняется для восстановления. Ошибка записи видна пользователю. Секреты не попадают в JSON и сообщения.
3. Сохранение файлов: длительные хеширования учитывают отмену и показывают прогресс. Короткая операция перемещения после записи intent остаётся восстанавливаемой; отмена не оставляет неподтверждённое состояние.
4. Пути: сопоставление учитывает конфликты файлов с каталогами, регистр и служебные пути. Не менять существующие корректные назначения без необходимости. Старые загрузки и частичные данные не переименовывать автоматически при неоднозначности; безопасно остановить конфликтующий элемент с диагностикой.
5. Тесты: сделать достижимым сценарий 30+30, сохранить все актуальные проверки защиты данных. Отказ отдельного теста сообщает его имя; runner имеет ограничение времени.

## Удаление клиентского способа

Engine остаётся небольшим фасадом API, чтобы не переписывать UI одновременно. Удаляются исполнение Cloud Files, поиск/перезапуски клиента, --probe и зависимость запуска от cldapi.dll. Общие HistoryStore, FileRules, восстановление карт, FilePreserver и защита reparse points сохраняются.

В enum остаются All, Remaining, DownloadErrors, PartialFiles, IntegrityFailures. Числовые значения оставшихся элементов закрепляются явно, чтобы удаление соседних элементов не меняло возможное старое числовое представление. passes.jsonl читается как строковое имя режима; неизвестные режимы не становятся исполняемыми.

## Подготовка к будущей миграции

Не менять сериализатор и форматы ради чистки. Сохранить синтетические образцы settings, passes, history, inventory и состояния частичной загрузки. Выделять только необходимые границы: сохранение настроек, получение обновления, назначение путей. Большой архитектурный рефакторинг не смешивать с исправлениями.

После стабилизации следующий отдельный этап — экспериментальная .NET 10 сборка, чтение образцов старых форматов, размер пакетов, запуск на выбранных Windows и проектирование совместимого обновления. Решение о публикации принимается по результатам, а не по дате. Нужно учесть, что старый обновлятор видит только первые 30 релизов.

## Проверка результата

Базовые сборки и полные тесты x64/x86 уже прошли вне песочницы; результаты в `docs/testing/baseline-2026-10-18/`.
Для изменений: сначала воспроизводящий дефект тест, затем исправление, затем актуальный полный набор обеих архитектур. Проверки используют синтетические данные и fake HTTP handlers.
Системные сценарии: read-only/занятые настройки, отмена обновления после заголовков, остановка хеширования, конфликт A и a/child.txt, старые журналы и повреждённый хвост, отсутствие клиента и cldapi, сохранение выбранного режима при обновлении облака.

Производительность инвентаризации измеряется отдельно на 10k/100k записей. Новая БД или формат журнала не вводится без отдельного проекта и миграционных тестов; результаты измерения определят необходимость следующего этапа.
