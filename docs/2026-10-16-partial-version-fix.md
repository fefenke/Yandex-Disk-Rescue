# Исправление определения версии частичной загрузки после 1.0.5

## Причина

Список облачных файлов и сведения об отдельном файле могут возвращать разный набор хешей. В 1.0.5 появление дополнительного SHA-256 при неизменных MD5, размере и времени изменения меняло идентификатор версии. Следующий проход сохранял прежний временный файл и карту в архив вместо продолжения загрузки.

Пустые sparse-заготовки имеют полный логический размер будущего файла, но почти не занимают места на диске. Их логический размер нельзя считать объёмом скачанных данных или фактически занятого места.

## Изменения

- При наличии MD5 дополнительный SHA-256 не участвует в определении версии. MD5 уже входит в поле облачной версии. Если MD5 отсутствует, SHA-256 продолжает участвовать.
- Карты 1.0.5 с дополнительным SHA-256 распознаются для той же версии с MD5. Контекст истории, путь, размер и версия должны совпасть. Сохранённые участки проверяются по контрольным суммам до сохранения нормализованной карты.
- Записи о неудачной проверке из 1.0.5 продолжают блокировать автоматическое повторное скачивание той же облачной версии, даже если дополнительный SHA-256 больше не возвращается.
- Уже скачанная новая копия не удаляется лишь потому, что старая совпала по размеру без доступного облачного хеша. Старая сохраняется в «Сохранённые прежние файлы», новая занимает обычное место. Это не меняет быстрый режим предварительного пропуска существующих файлов.

## Проверки

В `SafeDownloadTests.MetadataRegression` добавлены проверки изменения набора хешей, продолжения после ошибки загрузки на следующем проходе, совместимости карты с подтверждёнными данными, изоляции контекста истории, сохранения старой блокировки, изменения SHA-only версии и сохранения обеих копий при проверке только размера.

Очистка не удаляет существующий архив целиком. Большой логический размер сам по себе не служит основанием для удаления.

## Тихая одноразовая очистка последствий

При первом проходе после обновления, после получения списка и до обработки загрузок, программа автоматически проверяет свой архив. Окна, кнопки и уведомления не появляются. Кандидат должен принадлежать текущему контексту сохранения: проверяются корневая метка владельца, сохранённая версия переноса, контекст в карте и характерное архивное имя. Карта должна быть корректной и не содержать ни одной записи об участках. Windows должна подтвердить отсутствие выделенных диапазонов sparse-файла. Полное чтение содержимого не требуется.

Карта и данные открываются эксклюзивно; проверка и удаление выполняются по тем же дескрипторам. Реальные предыдущие копии, файлы с участками, неподтверждёнными записанными данными, чужим владельцем, повреждённой картой или недостаточными доказательствами пропускаются. Символические ссылки и junction не обходятся. Занятые файлы и ошибки доступа оставляют очистку незавершённой для повторной попытки.

После завершения сохраняется `preservation/empty-sparse-105.done` в истории конкретного бэкапа: следующие проходы не обходят архив повторно. Отмена через «Остановить» и аварийное завершение не отмечают незавершённую очистку как успешную. Уже удалённые пары не требуют повторной обработки. Папки архива и записи о прежних версиях сохраняются.

Непустые карты нельзя очищать этим способом. Их возможное восстановление — отдельная операция: сопоставление с облачной версией и проверка контрольных сумм участков без перезаписи существующей активной загрузки. Сохранённые пользовательские файлы и файлы с ошибкой проверки остаются нетронутыми.

`PreservedCleanupTests` проверяет очистку пустых пар, сохранность непустых и неподтверждённых данных, повреждённых карт, обычных файлов и чужих контекстов; повтор занятого файла, одноразовую отметку, отмену и продолжение. Реальная папка пользователя не используется тестами.

## Остановка при подготовке истории

Чтение `history.jsonl` теперь проверяет отмену между записями. Отмена не поглощается обработкой повреждённой строки, а журнал открывается для добавления только после успешного чтения. API передаёт токен отмены в загрузку истории; также проверяет его вокруг чтения и десериализации сохранённого списка.

При остановке до формирования очереди не создаются новые полные CSV-отчёты по ещё не подготовленному списку. Уже сохранённая история остаётся на месте. Остановка активных загрузок по-прежнему ждёт завершения запросов и сохранения полученных данных. Отдельная операция дискового чтения или обработки одного JSON-объекта может закончиться до реакции на отмену; мгновенная остановка зависшего накопителя не гарантируется.

Полный набор self-tests окончательной комбинации исправлений прошёл на x64 и x86 16 октября 2026 года. Проверки использовали искусственные данные, включая тестовый токен для Windows DPAPI. Реальная папка бэкапа не изменялась.

## Пустые папки после очистки

После завершения очистки файлов отдельно удаляются пустые вложенные каталоги архива — снизу вверх, без рекурсивного удаления. Непустые каталоги, корневая папка и `.ydr-owner` остаются. Символические ссылки и junction не обходятся. При отмене или ошибке этап можно продолжить.

Отметка `empty-archive-directories.done` независима от отметки очистки файлов. Поэтому новый этап выполняется также при обновлении с 1.0.6, когда файлы уже очищены. При переходе сразу с 1.0.5 выполняются оба этапа; промежуточная установка 1.0.6 не требуется. После завершения обход не повторяется.
